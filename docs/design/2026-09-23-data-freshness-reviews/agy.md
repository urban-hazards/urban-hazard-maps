The fix technically aligns the health metadata with the map, but semantically destroys the integrity of the data warning. Residual risk: users will believe encampments dropped from 305 to 3, posing a massive false negative for hazards.

1. **Population**: Counting every row is the wrong population for `through`. The banner explicitly promises to show the "last *complete* date". Because `type="Encampments"` drives 99% of the volume, its failure marks the end of complete data. Letting a trickle of queue-matched rows artificially extend the date violates the banner's promise.
2. **Honesty**: It is profoundly dishonest. "Data through Jun 22" implies June's 3 records reflect the full reality, hiding a 99% drop in reported hazards. This creates a dangerous false negative for users relying on the map. The date must not move past the point of volume collapse. 
3. **Side effects**: Yes. If a single queue-matched record arrives within 14 days of today, `last_30d` becomes > 0 and `days_since` drops below 14. This prevents the feed from classifying as "stale". `prior_year_30d` will correctly reflect last year's high volume (type + queue rows). The ratio (e.g., 1 / 300) will be < 0.5, so `status` will become "degraded". While `index.astro` treats both "stale" and "degraded" as troubled, reclassifying an undeniably dead primary feed from "stale" to "degraded" based on a data trickle is semantically weak.
4. **Years & edges**: The June rows will not fall outside the `years` set. The `years` variable determines which annual JSON files to read (2025 and 2026). `_legacy_days` parses the *entire* file for those years to calculate `through`, so June is always found regardless of the 30-day window used for counts. Timezone edge: `_local_day` simply calls `.date()`. If `_parse_datetime` returns a UTC-aware object for a late-night Boston record, `.date()` extracts the UTC date (shifting it to the next day), misaligning `through` with local reality.
5. **Alternative A**: Clipping points to `through` is strictly better. While the 3 June cases are real, mapping them without the missing 300 creates a massive statistical bias. The map should visually enforce the "last complete date" guarantee, preventing June from appearing artificially safe.
6. **False confidence**: The test codifies a bug as a feature. It asserts that finding a lone June 22 queue record *should* extend the `through` date, validating the misleading behavior. It also hardcodes `today` to Sep 23 (making June 22 safely >14 days stale) but fails to test what happens if the queue record was created yesterday, which would improperly clear the staleness.
7. **Fallback date**: Changing `frozen` in `index.astro` to June 22 is wrong because `frozen` is the static fallback for the "last complete date" when the API is down. It hardcodes the same lie into the SSR fallback layer. It should remain May 27.
